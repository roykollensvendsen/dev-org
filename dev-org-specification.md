# dev-org – system specification

**Version 0.37 · 26 November 2026 · Implementation specification for the MVP**

## 1. Purpose and delivery

dev-org must run software projects on assignment from a named client. The client states the desired result and its priority. The organization chooses the approach, does the work, verifies the result, and shows what was delivered. It must be portable to a new PC, able to use several machines at once, and able to develop its own software.

dev-org is to be a modular layer over coding agents. Claude Code, Codex, and OpenCode must be usable as interchangeable agent engines, and new engines must be addable through adapters. The organization's tasks, roles, mandates, queue, and durable progress must be independent of the engines' internal conversation formats and delegation mechanisms. An agent engine is the coding agent's execution system; choosing the language model within the engine is a separate choice.

The first end-to-end delivery is to take a bug report from an external board, reproduce the bug, fix it on a working branch, open one pull request (PR), wait for CI without an active model session, and register the verified result on the issue. The project's mandate decides whether the delivery concludes at a ready PR, at merge, or at rollout.

"Shall" expresses a requirement on the finished system. The introduction order in section 11 separates the first delivery from later capability. Section 10 sets the binding standard choices for the MVP; changing them requires a recorded architecture decision. Later delivery steps can replace the choices through the adapter contracts.

## 2. Responsibility and authority

| Role | Responsibility and authority |
|---|---|
| Client | Commissions and prioritizes, sets the desired behavior, budgets, and standing mandates. Can pause, reprioritize, and resume the work. |
| Organization lead | Keeps the overall overview, routes decisions to the properly responsible role, and gives the client one consolidated status and only the questions that require that person's choice. Routine choices within the mandate are settled without escalation. |
| Orchestration service | Executes the organization lead's workflow in ordinary code: chooses qualified work, reserves resources, enforces mandates, reconciles pending issues, and keeps operational status. |
| Responsible worker | Owns the execution of one issue for a bounded period. Can delegate independent subtasks within the same mandate and budget. |
| Evaluator and CI | Verifies the result against agreed criteria. For significant changes the evaluation must be runnable independently of the session that implemented them. |
| Project integration and operations lead | Defines the requirements for merging, release, and any rollout. These three actions must be able to have different mandates. |

An order received by text, voice, or board must be tied to a sender, project, and stable order ID. The project must state who can change priority and mandate. A comment, error log, or text fetched from a repository must not alone be able to extend the mandates.

The client must be able to follow the organization through one consolidated entry point. Workers report blockages, decision needs, and finished results to the organization lead; the lead groups like questions, forwards only the necessary choices, and relays the answer to all affected issues. Technical information needed to finish a bounded subtask may go directly between workers, with traceability in the task. A worker must not start a new parallel session to take over work from an attempt that is still owned by an active worker.

### Organization roles and addresses

Roles describe responsibility and mandate boundaries, not a specific agent engine, person, or active session. A role can be filled by different qualified workers over time; one worker can fill several roles but must have one explicit responsibility per task. The task, attempt ID, and reservation determine actual ownership. A role or component address alone never grants publishing rights.

Each worker and role must have a stable identity. The organization must be able to address a message by organization, project, or program, component, role, and optionally task. Short names may be used only when they unambiguously point to one recipient. On ambiguity the system must show the options and wait for clarification; it must not guess or send to everyone.

The project setup must describe the program/project hierarchy, components, roles, responsibilities, constraints, and which issue types or decisions must be delivered to each role. The setup must be versioned, checked on load, and unavailable for change from the agent's work area. Missing, unreadable, or unexpectedly changed rule foundations must stop new tasks that depend on the rules and report a concrete blockage. Ordinary code changes must not require changing the organization rules.

### Priority and autonomy

1. Do the client's highest-priority, clarified work. Necessary subtasks inherit the priority through the worker queue, CI, test bench, and merge queue. Adapters must state which external queues can be reprioritized.
2. On "B before A", A must be checkpointed at a suitable interruption point. Release the resources B needs. Preserve valid checks and resume A afterwards. An already-started physical operation may run to a defined safe stopping point.
3. Spare capacity may be used on documented product and process improvements within their own budgets. A proposal must describe the observation, expected effect, and how the effect is measured. If no suitable candidate exists, the workers go idle.
4. Escalate only the part that requires a product choice, an extended mandate, or an unavailable resource. Ask one concrete question, save what the answer should wake, and continue independent work. Repeated identical questions must be grouped.
5. When all qualified workers for a project are inactive while clarified work waits, the organization lead is notified once for the contiguous idle period. The notification states the number of waiting and blocked issues and what could start the work. The period ends when a worker starts or the queue no longer has clarified work; a new idle period may notify again. Missing queue data must be shown as unknown, not as an empty queue.

## 3. Architecture and data ownership

Organization, project, and worker node must have separate identities. The same organization can run several projects. Several nodes can take part in one project. Each project has its own mandates, budgets, and source links.

| Component | Authoritative data and responsibility |
|---|---|
| External project board | Tasks, backlog, priority, acceptance criteria, dependencies, and decisions. No parallel task list in Git. |
| Git and PR service | Code, versioned project rules, build recipes, agent definitions, and history. Each working branch is tied to the issue. |
| Durable state store | Internal IDs, external references, reservations, events, checkpoints, wait conditions, and pending external operations. |
| Worker node | Runs a supported agent engine through an agent adapter in an approved execution environment. Advertises engine and adapter versions, enforceable capabilities, toolchain, simulator, capacity, and hardware. |
| CI and artifact store | Owns runs, builds, test evidence, and resource measurements. The board and work view link to the results. |
| Launcher and work view | The launcher chooses an approved program version. The work view reads events and shows who is doing what. Both work with zero active agent sessions. |

**Starting architecture:** One active orchestration service with a transactional database. Several PCs work through the service's API. This gives atomic assignment and simplifies relocation. If the service is unavailable, a node can preserve local work, but new assignment and publishing of results must wait until ownership is controlled. The MVP choices are set in section 10.

The first architectural views are in the [system diagrams](docs/architecture/system-diagrams.md): component responsibilities, ports and adapters, the sequences from GitHub issue to verified PR and from voice client to insight, the task lifecycle, the authorization flow and access insight, lease/handover between nodes, and the self-improvement loop. The lifecycle diagram follows the operational states in section 5; execution attempts and reservations are separate lifecycles. The diagrams show module boundaries and the normal flow; they do not replace the contracts or the error/retry rules in this specification.

### Human and agent interfaces

dev-org must be usable by both humans and agents. They must work against the same authoritative tasks, backlog, status, decisions, artifacts, and event history through interfaces suited to the actor: dashboard/web UI via API, and agent or voice clients directly via MCP or API. The dashboard is a separate client and is not an intermediary in a voice conversation. MCP is a tool entry point over the same workflow and policy, not a separate authoritative data source. An MCP client is not necessarily a worker; a human-driven analysis conversation uses the user's identity and project-scoped read rights. A2A can be offered as an optional adapter for communication and delegation between external agents; A2A identity and messages must be tied to dev-org identity, tasks, and traceability before they can affect work.

The API and its backing services own the workflow and policy. The web UI and agent protocols are clients, not separate sources of truth. An action performed from a human interface or by an agent must go through the same authorization and validation rules, but permissions are determined by identity, role, and mandate and need not be the same. Human decisions, agent actions, and automatic decisions must be recorded on the same timeline with actor, basis, and policy version. Humans must be able to inspect what the agents do, and agents must be able to read the status and limits necessary for the task without gaining access to unrelated data.

### 3.1 Module boundaries

| Module | Responsibility and boundary |
|---|---|
| Organization core | Plans from the board's tasks, distributes work, and manages reservations, priority, and budgets. Knows the agent adapter's contract, not the engine's internal protocol. |
| Identity and access | Authenticates humans, agent/worker identities, integration services, and trusted external agents. Creates a verified actor context for API and MCP; does not itself grant operational mandate. |
| Policy and mandates | Evaluates versioned rules and authorized mandates against identity, action, resource, and conditions. Decides without model calls and logs the rationale. |
| Access insight | Reads effective access and explains policy decisions through the identity and policy modules. Is read-only and cannot assign, change, or perform rights. |
| Agent adapters | Translate tasks, messages, interruptions, results, and the engine's approval requests. Cannot extend the mandate. |
| Execution environment | Creates, inspects, and ends isolated workspaces and processes. Enforces access to files, network, and local resources. |
| Integration gateway | Enforces mandates and active ownership for external actions. Performs them through adapters for board, Git/PR, CI, rollout, and test bench. Manages necessary service access. |
| State and events | Preserves operations, checkpoints, wait conditions, messages, and decisions. Provides traceability and a basis for resumption. |
| Knowledge and experience | Stores, finds, and versions learning records with clear scope, source, and status. Offers the same contract to all roles and agent engines; grants no mandates. |

The organization core owns the use case and asks the gateway for external changes. The gateway is the only control service that calls the adapters' mutating operations; no core, worker, API, or MCP code writes directly to the board, Git, CI, or other external targets.

Ports must be clearly separated from adapters. Inbound ports describe use cases the control plane offers; REST, MCP, and webhook entries are adapters that call these. Outbound ports describe needs the core asks for, such as `Persistence`, `WorkTracking`, Git/PR, CI, `ExecutionBackend`, artifacts, and knowledge; concrete adapters implement the contracts against providers or local resources. The core and an adapter must only connect through the port contract, without direct adapter-to-adapter calls. The ports are code/module contracts and are not in themselves grounds for separate processes or network hops. MCP tool groups are adapter entries to bounded use cases.

Modules must have explicit, versioned contracts. The first implementation may gather the core, policy, gateway, and state into one service. One microservice per module is not required. Agent processes, subprocesses, and the repository's executable content must nevertheless have a real isolation boundary against the control service, its state, and its access keys.

dev-org itself must follow the project requirements in section 4.2 from the first delivery. Module contracts must be testable with simulated counterparts, so that a worker can develop and check a module before all integrations are finished.

### 3.4 Extensions and modularity

Extensibility is a requirement from the first version. New agent engines, board/Git/CI integrations, local or external `ExecutionBackend` and `WorkerPoolProvider` adapters, `DecentralizedWorkProvider` integrations, knowledge backends, organization packs, and recipes must be addable through documented contracts without rewriting existing roles, core flow, or other integrations. Extensions must be optional: the core must start and work when a non-selected extension is missing or fails.

Each extension must have a machine-readable manifest file with a stable name and publisher, version, supported contract versions, dependencies, capabilities, requested rights, configuration schema, health check, and qualification status. Packs and recipes must additionally state which modules they compose, supported project/workflow types, install and migration steps, and how they can be removed. Undefined rights or incompatible contract versions give a rejected install with a concrete reason. Version and source are locked in the organization's setup; updating must show changes, dependencies, rights needs, and migration before activation.

The core offers capabilities through narrow, versioned ports. An extension can announce and request capabilities, but cannot grant itself a mandate, read internal database tables directly, or bypass policy/gateway. A failure in an extension must be isolated to the function that uses it and shown with extension ID and version. A change to a contract must have a compatibility rule, a migration note, and contract tests; a break requires a new major version or an explicit adapter.

The MVP must use modular packs in the same codebase/process where reasonable, with ports and contract tests; a general dynamic code runner or a microservice per extension must not be built. Untrusted or third-party code runs outside the control service's process in an approved execution environment. Architecture tests must enforce dependency direction and prevent project-specific packs or engine adapters from importing each other's internal logic or the UI's. A new standard case must first be solved with an existing contract; new abstractions require at least two real or simulated users, unless a clear security or isolation boundary requires it from the start.

A future organization hub is a catalog and distribution channel, not an authoritative runtime or control service. Packs and recipes must be validatable, previewable, and installable from a local/Git source without a hub; the hub can later offer search, publishing, and update notifications over the same manifest and signature model.

The extension ecosystem must have a lightweight model of ownership and maturation, inspired by subsystem maintainership, working groups, and experimental components in large open projects:

| Maturation state | Requirements and effect |
|---|---|
| Proposal | Manifest, purpose, scope, and expected owner role are registered. Can be developed and tested in isolation. |
| Experimental | Contract test and basic documentation pass. Limitations and the responsible maintainer(s) are shown. Use requires an explicit project choice; it does not become a default automatically. |
| Qualified | Relevant contract, security, compatibility, and regression tests pass. Can be chosen by compatible projects. |
| Recommended | Has documented maintenance responsibility, active bug handling, update cadence, and usage experience. Can enter standard recipes. |
| Deprecated | New use/install is discouraged or stopped from a stated date/version. Existing installs get a migration path and cannot be upgraded silently. History and source are preserved. |

Each module, pack, and recipe must have at least one maintainer role and a deputy or documented handover path. Responsibility covers compatibility, bug triage, documentation, and updating qualification. Maintainers decide ordinary changes within their area according to the contract. Cross-cutting changes to shared API, security model, data ownership, or mandates require a versioned RFC/ADR with consequence and migration plan, but the decision can be made autonomously within a pre-delegated change frame in section 9.1. Only changes that exceed the frame require an owner decision. Ordinary changes must go through automatic checks without manual approval per change.

Maintainer is a functional role that qualified agents or humans can fill. The scheduler must assign triage, documentation, compatibility updates, and qualification automatically to an available qualified maintainer, with priority, mandate, and budget. The absence of a particular person must not put the extension or independent work on hold. RFC/ADR is a traceable decision process, not automatically a human approval gate: the maintainer role can decide within standing mandate, also for protected change types that are pre-delegated; only changes outside the base frame require an owner decision.

No single maintainer must permanently be the sole approver or the sole source of operational knowledge. Qualification, test evidence, decisions, and handover notes are stored in the repo/events. When an extension no longer has active ownership or passes required checks, the status must change visibly and use be limited by risk level; this must not block independent modules or projects.

### 3.2 Policy, mandates, and enforcement

Every request that crosses a client or service boundary must have a verified actor identity. The identity types are human, agent/worker, integration service, and trusted external agent. The human keeps the same personal identity across dashboard, Claude Code, and voice clients, with separate sessions/connections that can each be revoked. A model or subscription account does not in itself give dev-org access. Agent/worker identities are separate from the human and are scoped to organization, project, role, and on demand task/attempt with time-limited credentials. Integrations have their own service identities and must not impersonate the user; the operations log preserves both the performing service and the initiating actor/delegation basis. External agent identities must be explicitly linked to a trust profile before they can affect work.

API and MCP must carry forward a verified `PrincipalContext` with actor ID/type, organization, project scope, client/session ID, delegation basis, and relevant task/attempt IDs. Authorization is the intersection of identity/membership, assigned role and project access, the approved MCP tool profile, and policy for the concrete action/resource. A tool profile limits which tools the client sees but grants no right; identity and policy are checked on every call. The client cannot itself choose or extend its authorized profile. Internal modules receive the same verified context; new interactive login is required at the trust boundaries, not between modules in the same control service. Missing, expired, or revoked identity gives denial by default.

Policy must express the organization's actions, such as changing a workspace, publishing a working branch, creating a PR, ordering CI, merging, and rolling out. The organization's boundaries may be narrowed by project and task. Delegation must only give a slice of existing mandate and budget. Repository content, agent messages, and engine settings must not be able to extend these boundaries.

Access insight is a separate, read-only use case over identity and policy. The versioned API offers `get_effective_access` and `evaluate_action`; MCP offers corresponding tools in a modular `access` group. The dashboard uses the same API. An actor can see their own effective access in the current organization-, project-, and task context. Insight into another identity or role requires its own `access.inspect_others` mandate and the same project scoping; a missing mandate denies without revealing whether an unrelated identity or policy exists.

`get_effective_access` shows permitted action classes, resource scope, conditions, limits, source/policy version, and evaluation time. The role view describes the role estimate; effective access for a concrete actor is always computed with identity, project, task, and current context. `evaluate_action` assesses a concrete action and resource with the same policy evaluator as the performing call and returns `allow`, `deny`, or `requires approval`, with an understandable reason, relevant conditions/evidence, and policy version. Both operations are read-only except for audit logging; they do not perform, reserve, or approve the action. They must never show credentials, secrets, or sensitive internal policy data.

An advance response is a snapshot, not a permission or a guarantee of later execution. The actual action is re-evaluated at the enforcement point with current identity, policy, ownership, and evidence. Access requests are logged with actor, target identity/role when authorized, scope, time, and result.

A decision must state `allow`, `deny`, or `requires approval`, with rationale, policy version, and any conditions. The evaluation must know organization, project, task, execution attempt, active ownership, the concrete action and resource. Where relevant it must also know code version, test evidence, budget, and expiry time. A missing necessary decision basis must not grant permission.

Standing mandates must give automatic execution within the mandate. An approval request must be concrete and scoped to action, resource, and validity. The answer is recorded durably and wakes the right issue. A rejection from the engine's or host's overarching rules must be reported; the adapter must not try to circumvent it. Actors must be able to read their own effective rights and request a non-binding policy assessment of a concrete action without starting a model session.

Policy decision and enforcement are separate responsibilities. The execution environment enforces local limits, and the gateway enforces external actions regardless of whether the request comes from a tool, shell, MCP, or a subagent. The worker must not get alternative write channels or service keys that bypass the gateway. Read access and access to the model provider must be scoped separately from publishing and operations.

The gateway must check the current mandate and ownership at submission, and coordinate submission with an ownership change. An already-submitted call may take effect after a mandate is withdrawn. This must be recorded as an in-progress operation and reconciled before a new owner repeats it; revocation must not be presented as a reversal of performed actions. Adapters must document how they find the result again when an external service lacks idempotency support.

Merge and rollout conditions must be tied to the concrete delivery and valid test evidence. Changed code or relevant integration basis requires a new assessment of the affected checks. Policy, approvals, and active rights must be inspectable without a model session.

### 3.3 Execution environment and sandbox

dev-org must own the administration of the execution environments and reuse existing isolation technology, such as OS sandbox, container, or virtual machine. A custom implementation of low-level isolation is not part of the first delivery. The first platform is Linux; the concrete backend is chosen and tested on the pilot machine. A rootless container is a possible starting choice. Containers and virtual machines must not be claimed to have identical isolation guarantees.

Each run must have an explicit profile for workspace, mounts, reading and writing, network, processes, CPU, memory, and runtime. The profile must also describe which model, package, and data services are needed. It must not give general access to the user's home directory, other tasks, the host's administrative sockets, or the organization's control state. Only explicitly scoped sharing is allowed.

Isolation must cover the whole agent process and its local helper processes, including hooks, plugins, local MCP servers, build scripts, and subagents. External MCP servers and connected services acting outside this environment must have separate access control. Allowed network domains do not in themselves grant authority to change data at the service.

The engines' built-in rights controls must be configured in line with the mandate. They must not be the sole enforcement of the organization's minimum requirements. The execution environment and agent adapter must state which requirements the combination can enforce; a necessary requirement that cannot be met must stop startup with a concrete explanation. No silent transition to weaker isolation is allowed.

Work in the sandbox must be secured in a checkpoint before the environment is removed. After interruption, remaining processes and resource use must be identifiable and terminable. Physical equipment must be reached through a bench service that enforces reservation, allowed operations, and safe stopping points; a general sandbox does not replace these controls.

## 4. Startup and swappable integrations

An engine-independent startup operation, proposed as `dev-org init`, must map the repo, CI, board, and available resources. It establishes project links, verifies build and tests from a clean working copy, and tries a representative issue. It must be rerunnable without doubling resources or losing local customizations. The engines' skills or plugins can offer `/dev-org:init` as an entry to the same operation; the project setup must not be owned by a particular plugin format.

For **new projects** it must establish the smallest runnable function with an acceptance test. For **existing projects** it must reuse existing CI, instructions, and ownership, document known failures at startup, and preserve in-progress work. The startup must also map components, links, and constraints for parallel work per section 4.2.

Board, Git/PR, and CI must have separate adapter interfaces. A project can for example use Redmine for issues and GitHub for PRs. The MVP starts with GitHub Projects v2/Issues, GitHub pull requests, and GitHub Actions. Redmine becomes a later board adapter. New adapters must be addable without changes to the agent roles.

The board adapter's internal work model must be provider-neutral and use stable internal project and issue IDs. A simple local adapter stores projects and issues as readable files in the workspace and implements the same contract as external board adapters. It is used first for development, contract tests, and small local workflows; it is not a parallel backlog when an external board is chosen as the project's authoritative source.

The MCP server is one protocol entry with modular, versioned tool groups: insight (status, timelines, and measurements), access (one's own effective rights and advance assessment of actions), work (assigned issues and checkpoints), messages (inbox, replies, and handover), and optional administration. The groups are registered separately with capabilities, rights requirements, and contract tests. The tool registry only advertises qualified operations the identity has access to; a human-driven analysis conversation can get read access without write tools. The groups are modules in the MCP service, not separate server processes by default. Insight responses must give source/event references, time ranges, and missing or stale measurements where relevant. Access tools follow the constraints and audit requirements in section 3.2. Every call goes through the same identity, validation, and policy layer as other clients. The MCP server has no direct database or provider access. MCP clients connect directly to the MCP server; the server uses the API/application layer onwards. The API contract stays primary and can be used by engines without MCP support. MCP gives tool access; internal durable agent communication goes through dev-org's message contract, while A2A is optionally used against external agent systems. Availability from a concrete voice app depends on the app's MCP support, plan, and client surface; other compatible MCP clients must also be usable.

Moving between board adapters must be supported with explicit export and import, not assume continuous two-way synchronization. The export format `dev-org.work.v1` is versioned and includes projects, issues, dependencies, status, priority, responsible role, labels, comments, links, and created/modified times where the source offers them. Internal IDs are preserved; the provider's IDs, URLs, and fields without a common counterpart are stored as named external metadata. Import must first be previewable with field and user status mapping, conflicts, and information that cannot be transferred. It must not overwrite target content without an explicit choice. After import, created, linked, changed, and omitted items plus lost or adapted fields are reported. Export/import does not guarantee lossless transfer of provider-specific features.

| Board adapter operation | Contract |
|---|---|
| Fetch or follow changes | Deliver external ID, revision, and changed fields. Support reconciliation after a break in the event stream. |
| Read issue and dependencies | Translate the project's own statuses, fields, and priorities into a common work model. Report missing properties at setup. |
| Register blockage, delivery, or PR | Update only owned fields. Detect concurrent changes and preserve the user's newer priority. Repeated submission must have the same effect as one submission. |
| Change project management system | Preview field mapping, open issues, dependencies, and data without a counterpart. Pause new assignments during final reconciliation. Switch the active write target only once the mapping is confirmed. Preserve the reference to the previous system. |

The internal issue ID must survive a board change. Such a change must neither create a new PR nor order CI by itself.

### 4.1 The agent adapter's contract

Claude Code, Codex, and OpenCode must have separate adapters. Use documented program interfaces where they exist. Engine and adapter versions must be registered and qualified together. An engine change must not require changes to the organization's roles, board adapters, or mandate model.

| Operation | Common contract |
|---|---|
| Report capabilities | State supported start, events, interruption, approval flow, resume, delegation, and usage measurement. Distinguish between supported, emulated, and unavailable. |
| Start work | Receive stable task and attempt IDs, goals, criteria, mandate, budget, workspace, and checkpoint references. A repeated start request must not create parallel owners of the same attempt. |
| Deliver message | Tie message ID, sender, and recipient to the task. Distinguish a received message from a processed message and a result. The organization deduplicates and reconciles delivery. |
| Follow run | Deliver normalized events for status, verified progress, blockage, approval need, usage, and termination. Preserve the engine's own references for debugging. |
| Interrupt and end | Confirm when work has actually stopped, what is secured, and which operations or processes are still ongoing. A received interrupt request is not a confirmed termination. |
| Continue or hand over | Resume the engine's session where supported, or start a new attempt from the organization's checkpoint. State which method is used. |
| Deliver result | Return artifacts, code version, test evidence, unresolved items, and a proposed next action. The agent's own assessment of "done" does not replace agreed checks. |

The adapter's capability description must be machine-readable, versioned, and qualified with contract tests. It must also state available tools and relevant constraints, for example whether the adapter can enforce time and usage caps, interrupt processes, or resume a specific session. The scheduler must choose an engine based on the task's required capabilities and an explicit task profile. A missing capability must lead to another qualified choice or a concrete blockage; it must not be assumed or hidden behind a generic "supported" status. Task profiles can restrict tools to e.g. reading, code changes, testing, or publishing. Tool access never by itself grants authority for an action; policy and gateway still enforce section 3.2.

The core must choose an engine based on the task's requirements and the adapter's documented capabilities. Missing usage measurement must be shown as unknown, not zero. A task with a hard usage cap must only start when the chosen combination can enforce the cap or an explicitly approved conservative limit.

The engine's internal subagents may be used within the same mandate. Organization tasks that need their own reservations, budgets, or handover between engines must be registered in dev-org. Durable messages between such tasks must go through the organization's event and message contract. The engine's internal messaging system must not be the only source of the organization's progress.

### 4.2 Project requirements for decomposition, decoupling, and testability

Each project must describe component responsibilities, interfaces, dependencies, and how components are built and tested. The organization must use this basis to scope tasks and choose safe parallelism. Missing decoupling must be surfaced as a constraint and can justify prioritized improvements. Separate services or independent rollout are not required without a documented need; a modular monolith can meet the requirements.

| Property | Requirement and observable basis |
|---|---|
| Component responsibility | Describe the component's purpose, code areas, and data it owns. State the responsibility point for changes touching several components. |
| Explicit interfaces | Describe public calls, messages, and shared schemas, relevant failure cases, and compatibility requirements. Consumers must be able to use the interface without depending on internals. |
| Known dependencies | Register dependencies in code, data, build, execution environment, and physical equipment. Unknown links must be marked and treated conservatively in planning and test selection. |
| Local verification | Give reproducible build and test commands, required versions, and test data. Use per-component tests and contract tests for the interfaces; document checks that still require the whole system. |
| Controlled counterparts | Use test doubles or simulators where they cover relevant assumptions. Clarify which conditions must in addition be tried against a real integration or hardware. |
| Isolated test state | Parallel runs must have separate data, temporary files, and other writable resources. Resources that cannot be isolated must be explicitly reserved. |

The mapping must distinguish whether a component **can be developed separately**, **can be tested separately**, and **can be delivered separately**. These properties must not be inferred from the code being in different folders or repos. Separate processes, services, or rollouts must be justified with e.g. isolation, operational need, or scaling, and weighed against added integration work.

For new projects the boundaries must be established in the smallest runnable solution and extended as needed. For existing projects the startup must record the actual state: components often changed together, tests requiring the whole system, shared files or data, and scarce resources. Documented deviations must give an adapted work and test plan; full rebuild must not be a general admission requirement. Work that cannot be performed and verified soundly with today's boundaries must get a concrete prerequisite or blockage.

Strongly coupled changes must be gathered under one responsible worker or carried out as a coordinated delivery. Independent changes can be distributed when test state and shared resources allow it. Each task must state affected components, contracts, and known dependencies. The mapping must be updated on relevant changes and used by the test planner in section 6. Durable architecture descriptions and contracts are stored in Git; improvement tasks and their priority live on the board.

Decomposition and decoupling must be prioritized from observed wait time, conflicts, test cost, or rework. An improvement issue must describe the expected effect and how it is measured, within the project's mandate and budget.

The practical working rhythm for preparing, assigning, and integrating parallel changes is described in the [work protocol](docs/development/work-protocol.md) and reinforced by the repository's [agent rules](AGENTS.md). These give working guidance and do not replace the requirements in this specification.

### 4.3 Messages between workers

Workers must be able to communicate with each other through the organization's durable message channel, also when they use different agent engines. Task cards, logs, and the engines' private conversation histories are not sufficient as a communication mechanism. Messages are addressed to stable worker or role identities and tied to organization, project, task, and optionally attempt. Role addresses follow the unambiguity rules in section 2.

The message channel delivers at least once. Each message has a stable `message_id`; recipients handle duplicates idempotently. A message must state sender, recipient, type, created time, schema version, and relevant task context, and can state `thread_id`, `reply_to`, expiry, priority, and artifact references. The types cover at least question, answer, status/blockage, delegation request, and handover/result. The service records separately that the message is queued, available, received, processed, rejected, or expired. The sender can see delivery status and thread without depending on the recipient's engine.

A message does not change task ownership, reservation, mandate, or authority. Handover of ownership must go through the task and reservation service. Message content is treated as untrusted input; text from another agent cannot extend the recipient's authority or bypass policy. Messages and status transitions are recorded in the event log, tied to the task, and shown on the timeline with the current access and editing rules.

The adapter must state how an active session can be reached: direct injection if the engine supports it, queueing to a safe stopping point, or resume from checkpoint. If the engine cannot receive messages during a run, the message must remain durably in the inbox until a safe point; the system must not start a competing session to deliver it. Waiting for an answer must only block tasks that actually depend on it. Independent work must continue, and answers must wake the relevant waiting tasks.

## 5. Execution, waiting, and resume

A task describes the goal and has a stable identity through its whole course. An execution attempt is one run that can succeed, fail, or be interrupted. The reservation gives time-limited ownership; the engine's conversation ID only identifies an associated session. A new attempt or engine change must not create a new task or extend the mandate.

| Operational state | Transition and expected action |
|---|---|
| Ready | There is an authorized goal, sufficient criteria, and available dependencies. The scheduler assigns the issue to a qualified node. |
| In progress | One execution attempt has one active owner with a time-limited reservation and an ownership number. Subtasks can have their own reservations. A session that is still active must be reached via message or control of the existing session; resume must not start a competing copy. |
| Waiting | Store the concrete wait condition, last verified progress, branch/commit, and next action. End the model session when it is not needed. |
| Ready for reprocessing | An event, user answer, or reconciliation fulfills the wait condition. Create at most one active continuation for the same event and state. |
| Completed | Agreed criteria are fulfilled and the result can be verified afterwards. An ordinary service can close the issue when machine checks are sufficient. |
| Paused or ended | Record the decision, reason, and any resume conditions. Stop new work. Securing, cleanup, and safe stop may use a bounded shutdown reserve. |

### 5.1 Dynamic movement of work and sessions

The scheduler must be able to move work between qualified nodes when capacity, priority, node health, maintenance, network conditions, or required engine/hardware capabilities warrant it. Movement must happen only when the expected benefit is greater than the cost of securing and resuming the work; ordinary queue jitter must not lead to repeated moves. The rules and thresholds for movement are observable and tunable within section 9.2.

The standard way to move a run is controlled checkpoint and handover: ask the source to stop at a safe point, secure code/artifacts, test evidence, messages, wait conditions, and the next action, end or confirm the stop of the old process, transfer ownership with a new fencing token, and let the receiving node continue from the engine-independent checkpoint. A new node must never start before the old owner has stopped or fencing makes it unable to write or publish. Unsecured local work must be shown as risk and cannot be presented as handed over.

A live process or model session can only be moved without a restart when the adapter explicitly advertises and passes such a migration capability for the relevant engine version and both nodes. This is an optimization, not a prerequisite. If the engine cannot export or resume the session, work must continue from the organization's checkpoint with relevant message and learning context; the internal conversation history is not guaranteed. Login tokens and subscription credentials are never moved between nodes. The receiving node must itself have qualified, separate authorization for the chosen engine.

The movement decision, reason, checkpoint, source/target node, lease transition, any lost context, and result are logged and shown on the same task timeline. A failure in movement must safely recover or keep one owner; if the outcome is unclear, only the affected task is paused for reconciliation.

Assignment and registration of the next action must be atomic. Only the active reservation owner can change attempt status or trigger publishing; an old or duplicate session must be rejected by the service. Before an external call the service must preserve the intent and a stable operation key. After a crash it must find again an active session and any already-created PR, CI job, or board update before attempting to start or send again. Before publishing, the active ownership number must be checked, also when an old node returns after a network break.

A timeout after submission means an unknown result until reconciliation has clarified the outcome. A new owner must take over the registered operations and their keys. Coordination of ownership change and external submission follows section 3.2.

The organization's state machine is authoritative for task status, ownership, wait conditions, approvals, and whether an external action was performed. The engine's thread, conversation, or session IDs are only references to executions and cannot alone move an issue to a new state. Pauses and approval needs must be stored as durable state transitions, so that they survive the engine, node, or service stopping. An approval must be bound to a stable request ID, the exact action and resource, the relevant content/code version, mandate conditions, and expiry. If this basis changes, the request must be reassessed. Denial, expiry, and change of a request must also be recorded and wake the right issue.

Resume and retry must be idempotent at the organization level. Before a continuation is created, the service must check that the triggering event or approval has not already been processed and that the same attempt has no active continuation. External side effects must go through the operations journal and the gateway's stable operation keys. A checkpoint or replay alone does not guarantee that an external call happens only once; after an uncertain answer, reconciliation is required before renewed submission. Agent state can be stored to continue an engine session, but the organization's state and event history must be sufficient to hand over to a different engine.

An engine-independent checkpoint must contain the goal and criteria revision, mandate and policy references, secured code or archive, test evidence, decisions, unresolved items, wait conditions, ongoing external operations, and the next action. The engine's conversation ID is an optional additional reference. Handover must be able to start in another engine without importing internal conversation state. Valid checks are preserved; the recipient must verify that the basis still applies.

Register the wait condition durably and check whether the event has already occurred. Periodic, cheap reconciliation must fetch lost events. An inactive queue must entail zero model calls and zero active agent processes. A durable receiver for events must still be available, or be wakable by the infrastructure.

**Progress requirements:** The project states a measurable deadline from "ready issue and free qualified capacity" to start. Heartbeats and verifiable progress are measured separately. On repeated failure a bounded attempt and cost budget is used. The service can switch strategy, hand over, or escalate. On total resource shortage the view must state what blocks and what would wake the work.

## 6. Test cost, integration, and conflicts

- **One test planner.** Local agent and CI must be able to compute the same test selection from diff, component dependencies, changed requirements, and check rules. Unknown impact triggers a broader test group. A priority change triggers no build.
- **Reuse per check.** Compute the identity from relevant inputs, including source content, build flags, tools, tests, and environment. Two concurrent requests for an identical check share the run. A valid result can be reused. Hardware tests also require known conditions for bench, firmware, and calibration where these affect the result.
- **Mutation testing.** Run targeted mutations on affected logic where it contributes to the acceptance criterion. Broad runs have their own budget and lower priority. Changes outside the incremental tool's field of view must invalidate relevant results.
- **Scarce resources.** Reserve the physical bench when the candidate is ready. Use the simulator before the bench when it covers the same assumptions. Separating queue time from run time must make it possible to regulate the number of concurrent issues.
- **Concurrent code changes.** Use isolated working copies, short branches, and one responsibility point per delivery. Register planned changes in shared interfaces early. The integration test runs on the combination that will be merged. Stale jobs are ended when no consumer needs the result.
- **Contract changes.** Designate one responsible for the new contract, affected consumers, contract tests, and transition plan. Where appropriate, introduce compatible support first, move the consumers, and remove old support afterwards. If a compatible transition is not possible, plan one coordinated delivery and verify the whole combination before merging or rollout. Splitting into subtasks must not assume all workers finish at the same time without such a plan.
- **Feedback.** A failure in a broad post-check is tied to the right change, the responsible issue, and the gap in the test selection. Changing the check rules themselves requires the project's special mandate.

Use the [work protocol](docs/development/work-protocol.md) when tasks are to be distributed between workers or agents. For parallel or cross-module work, the [dev-org-parallel-work](skills/dev-org-parallel-work/SKILL.md) skill is also used as an operational checklist; if it deviates from the spec, the spec applies.

## 7. Portability and multiple machines

### 7.1 Control plane and worker nodes

Scaling across machines must happen by adding worker nodes against one authoritative control plane. The control plane owns the queue, task status, policy, reservations, ownership numbers, events, and external operations. Worker nodes execute assigned work in local, isolated environments. They connect to the control plane through the versioned API and must never read or write the control plane's database directly.

Each node is registered with a stable node ID and reports heartbeat, program/runner version, operating system, available agent engines and adapter versions, toolchain, CPU/memory/disk, network properties, simulators, and any physical hardware. The scheduler only assigns tasks the node's qualified capabilities and security profile satisfy. Node capacity and concurrency limits are enforced per node and project; several machines must not share the same local working copy or writable test state.

Worker nodes fetch tasks with a time-limited lease and a unique ownership number/fencing token. They renew the lease while working; on a network break they can secure local work, but they cannot start new external side effects or publish after the lease has expired or the control plane is unavailable. A node returning with an expired token can only deliver checkpoint/diagnostics for reconciliation; it cannot change task status or publish. A new owner can take over only after the control plane has clarified the lease and external operations.

Code and checkpoints are moved between nodes via Git or a controlled artifact store with content reference and integrity check, not via shared local directories. The checkpoint must be engine-independent as stated in section 5 and contain enough basis to continue on another node. Model, board, and other service accesses are issued separately and least-privilege; the worker's secrets are never mounted in the agent's sandbox.

Nodes use authenticated encrypted transport to the control plane, preferably over a private network/overlay or an equivalent restricted entry. They need no incoming open ports for normal task fetching. Worker tokens are node- and project-scoped, revocable, and stored outside the repo and the attempt container. The control plane can set a node to `active`, `draining`, `offline`, or `revoked`: draining stops new assignments and lets active attempts finish or hand over; revoked rejects further publishing and requires reconciliation of active attempts.

The first rollout can have the control plane and one worker on the same PC. More PCs are added through worker registration without moving authoritative state. The system must measure queue time, worker utilization, lease losses, handovers, and bottlenecks before the control plane is split or the database replicated; several nodes are not in themselves reason to introduce an HA cluster or distributed database.

### 7.2 External execution platforms and organization instances

dev-org must reuse existing platforms for creating and isolating external execution environments. It must not build its own general cloud/VM provisioner or a decentralized compute marketplace. Integration happens through two provider-neutral contracts: `ExecutionBackend` for creating, inspecting, connecting to, running commands, following processes, securing/restoring checkpoints, and ending sandboxes/VMs; and optional `WorkerPoolProvider` for creating and operating worker nodes when an external platform does not offer this as a managed function. APIs, resource names, wallet/token models, and the provider's core types are kept behind the adapter.

A versioned `ExecutionProfile` describes desired CPU/memory/disk/GPU, operating system, sandbox/VM isolation, network, region/data residency, lifetime, attestation requirements, cost limit, and required agent engine/adapter capabilities. The adapter reports what it can actually enforce and measure, with provider reference, cost, and lifecycle status. A missing requirement gives a concrete blockage or an explicitly approved alternative; silent weakening must never happen. The profiles are provider-neutral and pinned at run time. Changing backend requires previewing capability differences, migration cost, and data storage location.

Kubernetes or an equivalent container orchestration system is an optional `WorkerPoolProvider` basis for an own worker fleet; it is not part of the core and does not replace sandbox/runtime qualification. Infrastructure as code, such as Terraform, OpenTofu, or equivalent, may be used to create durable base infrastructure or dedicated organization cells. It must not be run uncontrolled by the agent for each task or used as a task queue. When a managed execution platform offers sandboxes and autoscaling through an API, dev-org can integrate directly without operating Kubernetes or Terraform.

Providers such as Targon, Hippius, Lium, and similar are assessed per concrete service and documented interface, not as one common cloud type. A service with a sandbox/job API connects directly as an `ExecutionBackend`. A service delivering VMs or a managed Kubernetes cluster can additionally be used under a `WorkerPoolProvider`; Kubernetes then manages the workers inside the cluster, while dev-org keeps the task, policy, and tracking responsibility. Terraform/OpenTofu can be an optional bootstrap layer when a qualified provider or other supported API integration exists for the infrastructure in question. No integration must assume that a Bittensor service automatically exposes Kubernetes or has a Terraform provider. If such an interface is missing, the direct API/CLI the adapter supports is used, or the service is not yet qualified.

Task distribution must not go through Terraform state or an infrastructure deploy per agent task. The agent can propose a declarative desired capacity within the mandate; a restricted adapter performs plan/apply or the provider's API calls, logs changes and cost, and can roll back/clean up. Provider and wallet secrets remain in the adapter's secrets boundary. A Kubernetes namespace, container, or VM alone does not count as a sufficient sandbox: concrete runtime isolation, network, identity, logging, and fencing must be qualified separately.

If a backend offers managed autoscaling, dev-org uses it through its API; dev-org only controls desired capacity, task distribution, and upper budget/count limits. If the backend requires its own worker hosts, a `WorkerPoolSpec` describes desired node count, capability requirements, network, and cost frame. An autonomous scheduler can adjust the pool within standing mandate. Nodes are registered through `worker join`, get project-scoped identity, and are drained before termination. Agents never get the provider's provisioning keys or control over the account/wallet root. Infrastructure cost, any execution platform fee, and model/subscription cost are reported separately.

Spinning up "organization parts" means by default creating extra worker pools or project-scoped capacities that connect to the same control plane; they do not share a database or working copy. Spinning up a whole organization means instantiating separate organization identity, policy, database/data store boundaries, board/repo references, packs, and mandates from a versioned template. Organization instances can later share a management/hub service for catalog and billing, but not authoritative work status, secrets, or policy. The topology must be selectable per installation: existing control plane with external workers first; dedicated control plane cells when isolation, load, or organization ownership warrants it.

Creation, retry, and termination are idempotent and recorded in an external operations journal. After a crash the adapter reconciles created environments before trying again; unused/orphan resources are detected and cleaned up within budget. External execution environments must pass the same sandbox, network, logging, heartbeat, fencing, and agent adapter qualification as local workers. Provider credentials are held in the adapter/control plane's secrets mechanism and never exposed to the attempt environment.

Decentralized networks such as Bittensor are connected through a `DecentralizedWorkProvider` adapter for a concrete, qualified service or subnet profile. The Bittensor chain, subnet choice, miner/validator identities, consensus, and token economy must not enter the organization core's task or policy format. Such a provider can only receive scoped subtasks and approved artifacts; the result is untrusted until hash-checked and independently verified in dev-org's approved test environment. Code, data, or context not approved for external processing must not be sent out. Validation scores or network incentives are not in themselves evidence of correctness, confidentiality, or fulfilled acceptance criteria.

Subscription login for agent engines cannot be assumed portable or identical on all cloud profiles. The adapter and execution environment must announce whether the chosen provider's official subscription login is supported on the concrete host type. Use the native/provider-supported authorization flow per worker; do not copy raw subscription tokens between machines or let dev-org intermediate/store/resell model usage. If the engine or account cannot be qualified in the cloud, use another qualified engine/access profile or mark the issue blocked.

A snapshot must contain schema and program version, organization and project identity, external links, operational status, wait conditions, and checkpoints. All changes that must survive a move, including work in local working copies, must be present in a confirmed working branch or a verified archive. Store artifact references with integrity check and state which external services must be available at restore. Access keys are fetched separately.

The image must also contain versioned mandate and policy references, approval decisions, engine and adapter versions, and execution environment profiles. Restore must check that the target machine can enforce the requirements and re-evaluate current mandates. An old image must not re-introduce revoked rights. A missing engine can be replaced through handover from a checkpoint when another qualified engine is available.

| Proposed command | Observable result |
|---|---|
| `dev-org snapshot` | Briefly stops new assignment, secures active work results, and creates a consistent image. Reports any unsecured data. |
| `dev-org restore <snapshot>` | Validates version and references, restores the state, and reconciles with board and CI. Active take-over requires the old service to be stopped or to have lost publishing rights. |
| `dev-org worker join <organization>` | Registers an additional node and its actual capacity against the same queue. |
| `dev-org worker drain <node>` | Stops new assignments to the node and shows active attempts that must finish or hand over before it is removed. |
| `dev-org worker revoke <node>` | Withdraws the node identity; reconciles active leases and blocks the old node from publishing. |
| `dev-org execution plan <profile>` | Previews the chosen backend, actual capability, region, data storage, cost, and deviations without creating an execution environment. |
| `dev-org execution apply <profile>` | Creates the execution environment via a qualified adapter within the project's authorization and cost frame; returns an external reference and internal node/attempt link. |
| `dev-org worker-pool plan <pool>` | Previews the desired worker pool, capabilities, budget, and node count without creating resources. |
| `dev-org worker-pool apply <pool>` | Asks a qualified `WorkerPoolProvider` to create or change the pool within an authorized profile; returns registered node IDs. |
| `dev-org org instantiate <template>` | Previews and creates a separate organization instance with its own IDs, data/policy boundaries, and link references. |
| `dev-org project add <repo>` | Creates a separate project link with its own adapters and mandate. |
| `dev-org status` | Shows tasks, blockages, active nodes, and the next expected event. |

On a sudden machine loss only the last secured work can be guaranteed. Each project must state the tolerated loss since the last checkpoint and recovery time targets. These targets are tested with an actual recovery on another machine.

## 8. Logging, traceability, insight, and optimization

Observation must be part of the first prototype. An operator must be able to find what the organization is doing, why an action was chosen, what it waits for, what is verified, and where time and resources are spent. The decision basis must consist of recorded rules, relevant inputs, short rationales, and test evidence; it must not assume access to the model's internal reasoning.

### 8.1 Structured events and traceability

Core, policy, gateway, execution environment, and agent adapters must deliver a common, versioned event format. Log at least ordering and priority change, assignment, start and stop, delegation and handover, significant tool operations, policy decisions, waiting and waking, checkpoint, test result, publishing, failure, and completion. Tie long-running operations to both start and end; a missing end must be shown as unresolved or in progress.

| Field group | Required content where relevant |
|---|---|
| Event | Unique event ID, event type, schema version, source, source's sequence number, time at the source, and time of durable receipt. |
| Context | Organization, project, task, and attempt IDs; trace ID for the run; parent operation and triggering event. The identities must link several attempts to the same task. |
| Actor and basis | Worker/node, engine, model when known, adapter and program version, code version, mandate/policy reference, and execution environment profile. |
| Action and outcome | Action, scoped resource reference, operation key, status, failure category, decision basis, and references to result or test evidence. |
| Measurement | Duration and resource usage with unit, measurement source, and whether the value is measured, estimated, or unknown. |

Stable IDs must follow the work through agent, gateway, PR, CI, and test bench. When an external service cannot receive the trace ID, the adapter must store the link to the service's own ID. The view must distinguish agent-reported progress from verified results and measurements from the services.

State changes and required audit events must be recorded atomically in the durable store, or through an equivalent documented mechanism that survives crashes. Recorded events must not be overwritten by workers; corrections and later clarifications become new events. Duplicate or delayed events must not give double consumption or wrong status. Sequence and causality must be preserved even when the nodes' clocks differ. Gaps in tracing must be marked, not filled with assumed progress.

### 8.2 Work view and diagnostics

The work view must start with the client's priorities. From a task it must be possible to follow subtask, performing human/agent/CI job, node, project, component, PR, and test evidence. Show what is happening now, what the last verified progress was, and what is expected.

For agent work the view must show engine, model where known, adapter version, execution attempt, and execution environment profile. A blockage must distinguish missing mandate, rejection in the engine or host, insufficient isolation, budget, and product clarification. Show which rule decided a rights request and what could wake the work.

From the overview the operator must be able to open a timeline per task and follow the causal chain to a concrete action, test result, or blockage. Show the last heartbeat, last verified progress, next action, responsible actor, and how long the issue has been in the current state. State when data was last updated; a stale view must not appear current. The view must be filterable by project, component, actor, engine, status, and time range.

Notifications must distinguish conditions the system handles automatically from conditions that require a human decision. Like failures must be grouped into one event with affected issues. The project must state limits for missing progress, long waiting, repeated failures, and budget use. When a blockage is resolved, it must be clear what resolved it and which work was woken.

A diagnostic package must be able to export a scoped task or time range with events, configuration versions, checkpoint references, and relevant logs. The export must state missing or expired artifacts. It must be usable for failure analysis without access to the original agent session.

### 8.3 Measurements and controlled improvements

The component map must show a selectable time range and distinguish model cost, active agent time, CPU time, bench time, queue time, and rework. Mark unknown component or cost explicitly. A shared CI run counts once in the organization's total; any distribution between tasks must be marked as an allocation rule, not as extra actual consumption. Also show the reason for each expensive check, the number of reused results, and how often humans had to intervene.

Small structured events from worker, CI, and bench must drive the view. Ordinary measurement, prioritization, and waking must work without a language model. Project budgets must be able to govern concurrency, time, and API usage separately for tasks and background improvement.

| Question | Measurement |
|---|---|
| Is the organization delivering faster? | Time from order and from ready issue to verified delivery, with waiting and active execution separate. Show distribution and number of issues. |
| Is it delivering correctly? | Share of issues passing the agreed assessment, rework, reopened issues, and failures discovered after delivery. |
| Where are humans needed? | Number of interventions and time spent per delivered issue, categorized by product choice, mandate, access, failure, and missing progress. |
| Is the organization standing still? | Qualified workers inactive while work waits, number of waiting and blocked issues, duration of idle time, and which event or resource would start the work. |
| What does each agent and role do? | Tasks received, started, completed, interrupted, and handed over per actor and role; time in queue, active work time, and wait time split by cause; handovers and whether they led to verified progress. |
| How reliable is the delivery? | Share passing agreed checks on first try, rework, reopenings, and post-delivery failures, split by actor, role, engine, and check type where the data basis allows. |
| What does the delivery cost? | Model/API usage, agent time, CPU and bench time per task and verified delivery, including failed attempts. Token usage and billed or calculated cost must be kept separate. |
| Where does the flow stop? | Queue and wait time per cause and resource, number of concurrent issues, handovers, conflicts, and repeated attempts. |
| What does test reuse save? | Number of reused checks, actually executed runs, and any estimates of saved time or cost, clearly marked as estimates. |

Workload and contribution must be displayable per agent, human, functional role, engine, and project. An agent covering several roles, and a role performed by several agents, must be distinguishable in the measurements. Preserve the task and attempt IDs at handover, so that visible activity is not counted as several completed deliveries. Separate raw activity from achieved result: the number of tasks or tool calls is not in itself a measure of value.

Comparisons between actors and roles must show issue volume, complexity, uncertainty, priority, wait conditions, and available basis where known. Be explicit when the comparison basis is too small or skewed. Do not rank or reward agents based on raw activity, issue counts, token usage, or speed alone. Use the measurements to find bottlenecks, skewed work distribution, costly rework, and areas for better tools or task scoping. No result-based decision must be based on incomplete or unknown measurements as if they were zero.

An optimization must have a hypothesis, a baseline measurement, a scoped change, and a criterion for improvement without unacceptable quality degradation. Compare on a versioned set of representative tasks with recorded engine, model, code, test, configuration, and environment versions. State the number of repetitions, variation, cache/reuse ratio, and unknown measurements; one fast run alone is not evidence of an improvement. Failed, interrupted, and unresolved issues must be included in reporting, not only successful deliveries.

Recorded events must be replayable against queue, policy, and state machine with a simulated clock and simulated external adapters. Replay must be isolated from active queues, publishing accesses, and physical resources. It verifies the control logic; new model runs are separate, budgeted experiments and are not expected to give identical answers. The basis for an adopted improvement must be linked from the improvement issue.

### 8.4 Operations and scoping of log data

Distinguish necessary audit events, operational measurements, and detailed debugging logs. Necessary events for ownership, mandates, and external actions must not be omitted by sampling. Detailed debugging logging can be enabled for a specific task or time range with limits on data volume and retention. Access keys and authentication data must not be logged. Complete task texts, code, and tool output must only be stored when the project's explicit logging profile allows it; otherwise use scoped summaries and access-controlled artifact references.

Insight and export must follow the project's access boundaries. The project must state retention and deletion per data class and which evidence must be preserved for recovery and verifiable delivery. A diagnostic package must follow the same rules and contain no access keys.

Failures in external log export or dashboard must not stop work when the necessary state and audit trail are still stored durably. Export must be resumable, and any dropped diagnostics must be counted and surfaced. If the necessary recording of ownership, mandate, or operation intent cannot be secured, the affected new actions must be stopped. Logging's own CPU, storage, and network usage must be measurable and limitable.

The first prototype can use the service's database, a simple timeline/status view, and export in JSON Lines format. A separate system for log analysis is not a requirement in the first delivery. The event format must make later replacement of storage and view possible without changes to the agent roles.

### 8.5 The organization's self-insight and self-diagnostics

The organization must be able to examine its own operation from incoming order to verified result, including control service, scheduler, queue, worker, adapter, agent engine, sandbox, gateway, board, CI, and storage. Each module must report heartbeat, capacity, queue depth, pending work, failures, retries, duration, resource usage, and dependencies where relevant. Interfaces between modules must have correlation IDs and measurements of calls, waiting, failures, and timeouts. A component map must show ownership and dependencies so that a slowness or failure can be traced to the likely bottleneck.

The insight must support three levels: (1) operational status and alerting, (2) reconstruction of individual issues and debugging, and (3) analysis of patterns over time and proposals for improvement. The view must let an operator go from aggregated symptom to affected module, task, attempt, event, and evidence. Each measurement must state source, time range, coverage, and uncertainty. Missing instrumentation must be shown as a separate deviation with affected modules and measurements; missing data must never be interpreted as zero failures, zero cost, or normal operation.

The organization must be able to run a periodic or requested retrospective on events and measurements: what failed, where the work waited, which capacity limits were reached, which failures were repeated, where rework arose, and which dependencies created queue. The retrospective must distinguish observed cause from hypothesis and state the sources supporting the conclusion. It must be able to create prioritized improvement proposals with a measurable hypothesis, proposed responsible module/role, expected effect, and evaluation method. The MVP must support insight, diagnostics, and proposals; changing active code, policy, budget, or production configuration still requires its own mandates, qualification, and activation gates in section 9.

Designated maintenance roles must have searchable, read-only insight into the necessary operational data across modules to debug and tune the system. Access to such insight must itself be logged. Secrets, subscription tokens, personal data without operational need, and complete model reasoning must not be exposed. Where raw tool output or message content is necessary for debugging, it must be access-controlled, time-limited, and clearly separated from the normal operations view.

### 8.6 Experience memory for roles and organization

Learning from tasks must be preserved as small, versioned, and searchable experience records, not as unbounded copying of conversation history. The knowledge module exposes versioned `propose`, `retrieve`, `feedback`, `review`, and `deprecate` operations through an engine-independent interface. Backend and search index can be swapped without changing role contracts; the first implementation can use PostgreSQL and need not have a separate vector database.

Knowledge is shared in clear, inheritable scopes:

| Knowledge space | Typical content | Access and sharing |
|---|---|---|
| Organization | Common ways of working, system operations, and documented general lessons | Can be used across when the record is checked, access allows it, and it is not project-specific. |
| Discipline/role guild | Discipline methods, checklists, and experience for e.g. testing, security, or adapter development | Shared between workers filling the same discipline role; independent of which engine performs the role. |
| Project/component | The repo's build, architecture, local conventions, integrations, and known pitfalls | Only available to authorized workers in the project or component. |
| Worker's working notes | Temporary observations and preliminary proposals from one worker | Private to the worker and relevant tasks until curated and possibly shared further. |

A worker can have several roles and thus fetch from several role guilds, but project/component access is always enforced. Working notes are not automatically copied between engines. Sharing happens by explicit proposal to a shared knowledge space with a stated target audience. A record must state scope (organization, role guild, project, component, or worker), problem/context, recommended approach or pitfall, source task and evidence, registration time, responsible for curation, and status. Status distinguishes at least proposal, checked, and refuted. Where the experience can become outdated, the record must also state the relevant code, tool, policy, or environment version and the time for a new assessment.

After a task, the performer or retrospective can propose a learning record when it points to a concrete outcome, test evidence, or repeated observation. Proposals must not automatically become an organization rule. They can first be used as clearly marked, uncertain guidance within their original scope; broader sharing from working note to project, role guild, or organization requires access control and curation. Organization learning requires checking against independent projects/issues or explicit curation. Refuted, conflicting, or outdated experience must be marked and removed from standard retrieval, but history and source must be preserved for audit.

Before a task starts, relevant records can be retrieved by role, project, component, task type, access, and version validity. The result must preserve each knowledge space's provenance; the module must not merge records so that scope, source, or conflict disappears. More specific project/component knowledge is shown together with relevant shared role knowledge, and on conflict both are marked with scope and basis. Project rule or policy always has precedence as normative basis; experience is guidance, not instructional authority. The agent must be able to see the record's status, source, and limitations. After use, the worker can register whether the advice was relevant, helped, was outdated, or led to error. This gives a basis for keeping, scoping, updating, or refuting the record.

The experience memory is reading support and cannot change mandate, authorities, mandatory tests, or policy. Searching and writing follow the project's access and retention rules. Secrets, raw credentials, and complete internal model reasoning must not be stored as learning. The MVP must support durable registration, source reference, scope, and status; automatic synthesis and promotion of learning can be introduced later with controlled evaluation.

### 8.7 Modular dashboard and insight into own development

The dashboard must be built from scoped view modules with versioned data and access contracts. A view module describes which measurements or events it needs, which filters it supports, how data coverage and freshness are shown, and how it fails. Modules must be activatable, deactivatable, and replaceable independently; a failure or slowness in one panel must not make the rest of the dashboard unavailable. The first version can use built-in panels in the same web app; arbitrary third-party code is not run in the user interface.

The project overview must show milestones, acceptance requirements, delivery status, quality, development flow, and bottlenecks with links to authoritative issues, PRs, events, and test evidence. When dev-org develops itself, it must be shown as an ordinary project with its own backlog, milestones, PRs, CI results, failures, and dependencies in the same dashboard. Progress must be derived from the board and verified events, not from the dashboard's own code or manually maintained percentages. GitHub/chosen board remains authoritative for backlog and priority.

The dashboard must also show its own operational health: last successful update, data sources that are delayed or unavailable, failures per view module, response time, and any incomplete measurement coverage. This health must be readable from a separate status/health endpoint or operational measurement, so that a failure in the dashboard does not hide that the dashboard has failed. The dashboard's frontend is never the authoritative source for tasks, policy, or project progress.

The view must be near real time. Durable internal events are pushed to clients after commit, and changed panels update without a full page load. The first delivery uses server push from the event stream; clients can fetch events after the last sequence number after a disconnect and fall back to bounded polling when the stream is unavailable. Changes affecting ownership, policy, or audit cannot be dropped; view updates may be batched for a slow client without losing underlying events. External data sources must show their own event/fetch delay separately from the view delay. The target for internal event to visible update is p95 under 2 seconds in normal pilot operation; on breach the delay must be shown and alerted per the project's thresholds.

The organization overview must aggregate status for all registered nodes and still allow drilldown per node. Show at least state (`active`, `draining`, `offline`, `revoked`), last heartbeat and data staleness, qualified engines/adapters and capabilities, CPU/memory/disk and available capacity, active leases/tasks, queue work the node can take, failures and recovery needs. State aggregated capacity and number of qualified nodes per project, but do not present disconnected nodes or missing measurements as free capacity. From a node the operator must be able to open the timeline of the attempts it owns; from a task one must be able to see which node and runtime executes it. The nodes' technical status must never hide task, policy, or delivery status.

## 9. Bootstrap and self-development

The dev-org repo can be the first pilot repo and must after startup be registered as an ordinary project with its own backlog. Before the first version exists, the smallest control core is built by a human-directed development process. dev-org cannot be the only tool for building, repairing, or starting itself.

### 9.1 The limit of recursive self-improvement

The specification makes room for **bounded recursive self-improvement (RSI)**: dev-org can propose and implement durable changes in its own software or workflow, and a qualified version can influence how later improvements are carried out. Humans set the mandate frame in advance; humans must not have to approve each individual change. This is not a mandate for autonomous, unlimited self-modification. The MVP does not include self-training or changing model weights.

Regardless of how much of the implementation work is automated, these limits apply:

- The owner sets a versioned base frame once and can pre-delegate clearly scoped self-changes. The base frame sets hard caps for allowed action types, project/repo scope, data and identity access, isolation, resource usage, risk level, and irreversibility. It can also contain inviolable goals, quality and security invariants, and required evidence. An agent cannot extend this frame, remove invariants, or give itself or another role more authority than the frame allows.
- Within the standing change frame the organization can autonomously change policy rules, role mandates, thresholds, test/evaluation setups, and operating profiles, also when the change type is otherwise protected. Each change must have a machine-readable change class, scope, rationale, expected effect, expiry/re-assessment time, and rollback plan. Changes that increase risk must use an explicit risk/resource budget; no single change or series of changes can bypass the frame's cumulative limits.
- Before activation a separate, deterministic control service must validate that the change stays within the base frame. Required tests and evaluators must be independent of the candidate. The change goes through an isolated shadow/simulation test and a graded canary with automatic rollback on breach of invariants, quality goals, or resource limits. The active organization continues to work under the previous valid version until the candidate is qualified.
- Only changes that extend the base frame, lower inviolable invariants, introduce new irreversible or external action types, or cannot be machine-classified/verified require an owner decision. Such proposals must sit in their own queue and must not block ordinary work or other self-improvements that remain within the current frame.
- Candidates are assessed against a versioned, human-approved basis. The agent can add proposed tests, but cannot remove or replace the mandatory regression and security suite used to approve the candidate.
- Comparison must use the same task set, evaluator version, and reporting measures for baseline and candidate. Results must include quality, check failures, resource usage, failed attempts, and uncertainty; a candidate is not accepted just because it is faster or cheaper. These are automated gates under a pre-approved mandate profile, not a new human approval per change.
- A change is classified by versioned risk profile. Changes within the standing frame can be activated autonomously after independent validation, even when they concern goal/evaluation configuration, policy, mandates, sandbox profile, or resource limits. They can never weaken mandatory invariants or exceed the hard caps. Changes to the identity/secret root, new irreversible or external action types, frame extension, destructive migration, activation mechanism, or rollback are outside the frame by default and require an owner decision. An unknown or ambiguous risk class is quarantined; only the affected change is paused.
- The agent that proposes or implements the change cannot itself issue the approval decision or modify the activation gate. A separate, predictable promotion service can automatically approve changes within a standing mandate when all criteria pass. Production rights, secrets, launchers, and rollback capability remain outside the agent's control.
- Extending the outer constitutional frame requires explicit owner decision, updated threat and failure analyses, and passing tests for the new mandate. The owner can, at establishment, delegate a bounded development path within this outer limit, so that operational limits can be extended gradually and automatically. Earlier success alone never grants permission to exceed the outer limit.

### 9.2 The learning loop for limits and mandates

The organization must itself gather evidence for how the limits affect both security and progress. It must record denials, near-misses, incidents, false positives, access wait time, tasks blocked by policy, overrides, rework, and the outcome of permitted actions. The organization must distinguish a necessary security boundary from a rule that is too broad or mis-calibrated; the number of denials alone is not evidence that a boundary should be widened.

Qualified agent roles can together propose a policy or mandate change with source events, expected benefit, risk, scope, and a measurable success/stop criterion. A separate policy controller checks the proposal against the outer frame. A challenger role tries counterexamples and abuse; an evaluator runs replay and regression/security tests; a promotion service only activates changes that pass every gate. The roles and the control must be separated from the proposing agent. Different agent engines can contribute assessments, but model disagreement or agreement does not replace deterministic checks.

Boundary changes must first be tried on historical events and synthetic abuse cases, then in shadow mode where decisions are logged without affecting active action, and finally rolled out as a scoped canary if the risk allows it. Compare against the baseline on both security measures (policy breaches, false grants, unresolved side effects) and flow measures (blocking time, rework, completion rate, cost). An unacceptable security deviation stops or rolls back the candidate automatically; better flow can never compensate for breaching an inviolable invariant. Each transition is versioned, has expiry/re-assessment, and can be reversed without stopping independent work.

The autonomous development path can increase or decrease operational mandates in small, measurable steps within the outer caps, pre-approved action classes, and resource/risk budgets. It cannot add a new irreversible action type, access the identity/secret root, remove the independent evaluator/rollback boundary, or change the outer frame. When evidence is missing or ambiguous, the current boundary is kept and only the affected proposal waits; other work continues.

Self-improvement must never block or delay ordinary, higher-priority work. It runs in its own low-priority, interruptible queue and uses separate candidate state, worker identity, and budgeted capacity. Production work has reserved CPU/memory, worker, CI, and API quota limits that candidate runs cannot use. When the reserve is threatened, an ordinary issue becomes ready, or a candidate loses its heartbeat, the candidate run is paused or ended first. If the platform cannot distinguish capacity or quotas well enough to meet this, self-improvement runs must be deferred or moved to a separate runner; they must not share a scarce production resource.

The candidate database, test board, queue, and CI state are separate from active operations. Activation is blue/green: the old version continues to handle active tasks while the candidate is started and health-checked. Ownership is moved only by controlled lease transfer; no rollout can require an in-progress issue or prioritized queue to stop. Database migrations must be backward-compatible and non-blocking for the active version. Destructive or long-running migrations are deferred until they can be done without putting production work on hold. On failure the old version continues, and the candidate's work is discarded or held without holding reservations or locks in production.

Thus dev-org can get better at improving its own ways of working, but a separate approval and activation boundary controls which changes become permanent in the active organization.

Bootstrap happens stepwise:

1. **Manually built core.** Implement the workflow in section 10 and confirm it on one small issue. Use GitHub Projects v2/Issues, OpenCode, and CI with human review. No automatic merging or rollout.
2. **Dogfooding in PR mode.** The active version can take small, scoped issues in its own repo, create a branch, and open a PR. During the bootstrap period the first PRs are reviewed and merged manually to qualify the evaluator and risk profiles. This is a scoped introduction gate, not a permanent requirement for all PRs. Start with documentation, scoped fixes, and improvements to insight; do not start with changes to its own mandates, sandbox, data migration, or rollout.
3. **Isolated candidate.** A new version is tried in its own test environment with a separate database, test board/project, worker identity, and limited GitHub rights. The candidate cannot read or write the active queue or impersonate an active worker.
4. **Controlled activation.** A separate launcher activates a qualified version after CI, acceptance tests, migration, and recovery path are checked. Changes within a pre-approved risk profile can be merged and activated without human approval per PR. The active version keeps ownership until controlled take-over. Rollback must be able to restore the previous program version and data state without losing already-registered external operations.
5. **Gradual autonomy.** Extend the automatic risk profile when fixed tests show reliable evaluation, non-blocking resource use, successful rollback, and resumption after interruption. Human decision is kept for the protected control areas above; ordinary low-risk changes must not wait for human approval.

Before the candidate version is activated, it is tried with interruption, priority change, and in-progress work from the previous version. The database schema uses backward-compatible migrations where possible; destructive migrations require documented backup, tested recovery, and a separate transition plan. Automatic improvements must pass the checks that applied when the issue started. Changes to its own mandates or rollout criteria cannot be approved by the agent that proposed or implemented them.

The first own improvement issue after a successful pilot should reduce the number of reconciliation calls without weakening the wake-up deadline or the protection against double continuations. Measure before and after per section 8.3, link measurements and event traces to the issue, and require that existing acceptance tests still pass.

## 10. MVP decisions

This section closes the open technical and operational choices for the first implementable delivery. The choices are binding for the MVP, not for all future installations. Changes are documented as an ADR with consequence, migration path, and updated acceptance tests.

### 10.1 Technology stack and operating model

| Area | Decision for the MVP |
|---|---|
| Language and API | Python 3.14.x, FastAPI, and Pydantic 2.x. Python 3.14 is chosen for the MVP because of a longer remaining support window than 3.12; FastAPI and the MCP Python SDK support 3.14. The API contract is published as OpenAPI 3.1. Patch versions of Python and all libraries, plus agent engine releases, are locked in reproducible build files. See [Python version status](https://devguide.python.org/versions/), [FastAPI release notes](https://fastapi.tiangolo.com/release-notes/), and [MCP Python SDK](https://py.sdk.modelcontextprotocol.io/get-started/installation/). |
| Durable state | PostgreSQL 16.x, SQLAlchemy 2.x, and Alembic. PostgreSQL is authoritative for internal tasks, reservations, approvals, operations journal, events, and queue. GitHub is authoritative for issue content, priority/status after project mapping, source code, PR, and CI result. |
| Queue and reliable delivery | No separate message broker in the MVP. The work queue, agent inboxes/outboxes, reservation, and transactional outbox live in PostgreSQL. Workers take tasks and messages with transactional locking (`FOR UPDATE SKIP LOCKED`). Delivery is at least once with idempotent processing. Board webhooks and CI webhooks are confirmed only after durable receipt; periodic reconciliation runs every 2 minutes as a fallback. |
| API and events | JSON over HTTPS under `/api/v1`. Resource changes use an idempotency key. Server-Sent Events on `/api/v1/events` deliver view updates; the client can fetch events after sequence number after a disconnect. Internal durable events use the versioned format in section 8.1. |
| Agent tools | One versioned MCP service offers modular tool groups as a thin client adapter over the API. The registry filters groups/operations by qualification, capabilities, and identity. The groups are not separate server processes in the MVP. The same identity and policy controls apply; direct database writing is forbidden. The API is still the primary contract; MCP support is qualified per engine and is not a requirement to use an otherwise-qualified API client. |
| User interface | Light, modular web UI in the same service for project/milestone overview, backlog, quality, flow, bottlenecks, timeline, approvals, and blockages. The project's own development is shown from the same authoritative board and event data. The API is the primary contract; the UI must not contain authoritative workflow logic. |
| Distribution | One Linux control node runs the API, PostgreSQL, and scheduler. A separate worker process runs on the same node in the first pilot; it can later move to other PCs without moving authoritative state. No HA cluster or Kubernetes in the MVP. |
| Migration and backup | Alembic migrations. PostgreSQL backup every 15 minutes to a separate encrypted storage target, daily full backup, and WAL archiving. Recovery is tested before the pilot is activated. |

The core uses a versioned `Persistence` interface for durable internal state; core and agent modules do not send database-specific queries directly. PostgreSQL is the first MVP implementation because the control service must coordinate several workers with atomic leases, queue, inbox/outbox, and event/state writes. It is a reasoned operational decision for this operating model, not a requirement for board adapters or local workflows. The port covers transactional writing, idempotency, reservations, queue, inbox/outbox, and consistent reads. PostgreSQL-specific capabilities are documented. Another database can be qualified with the same contract and recovery tests; a product change requires an ADR and migration plan. This gives swappability without promising that all databases are directly compatible.

The core objects in the first data model are `Organization`, `Project`, `Task`, `Attempt`, `Reservation`, `Worker`, `Approval`, `ExternalOperation`, `Checkpoint`, `Artifact`, `ExperienceItem`, `PolicyVersion`, and append-only `Event`. All have an internal stable ID. `Task` points to external board IDs; `Attempt` points to the engine's session ID as a nullable runtime reference. An event and a state change are written in the same database transaction; outbox publishing can be repeated without duplicate effect.

The event schema `dev-org.event.v1` has required `event_id`, `event_type`, `schema_version`, `organization_id`, `project_id`, `task_id`, `attempt_id` when relevant, `source`, `source_sequence` when available, `occurred_at`, `recorded_at`, `causation_id`, `idempotency_key` for side effects, and a typed `payload`. Time is UTC ISO 8601. The schema is validated on load; an unknown version or invalid critical event is quarantined and cannot change authoritative state.

The minimum operations in API v1 are `GET/POST /projects`, `GET /tasks`, `POST /tasks/{id}/dispatch`, `GET /tasks/{id}/timeline`, `POST /tasks/{id}/pause`, `POST /tasks/{id}/resume`, `GET /approvals`, `POST /approvals/{id}/decision`, `GET /runs/{id}`, `POST /runs/{id}/cancel`, `POST /webhooks/github`, and `GET /events`. Mutations require an `Idempotency-Key`; approval and publishing operations re-check policy at execution. Route changes that break compatibility require a new major version.

### 10.2 Integrations and first delivery

| Integration | Decision |
|---|---|
| Board | GitHub Projects v2 with GitHub Issues is authoritative for the externally connected MVP pilot. A local, file-based adapter implements the same board contract for development and contract tests. The project setup states the active adapter; two active write targets for the same project are not allowed. The GitHub setup states Project ID, repository, status field, and priority field. The first statuses map to `Ready`, `In progress`, `Blocked`, `In review`, and `Done`; unknown statuses automatically stop assignment for the issue. Export/import uses `dev-org.work.v1` as defined in section 4. |

Claude Code is engine number two in step 2 and must use the user's native Claude Code subscription login. Codex App Server is engine number three in step 5 and must use the user's qualified ChatGPT/Codex plan login. | Sandbox | Rootless Podman on Linux, one container per attempt. No privileged container, host network, Docker/Podman socket, or control service secrets are mounted. GitHub webhooks are verified with the HMAC signature before durable receipt, and the webhook secret can only be read by the gateway. The adapter must test the concrete GraphQL and REST operations the setup needs against the install's rights; a general rights list is not evidence that all Project fields can be read or written. See [GitHub's guide to choosing App permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app) and [the GitHub Apps permissions matrix](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps). The OpenCode adapter follows OpenCode's documented headless/agent interfaces; RPC methods and event types are qualified against the pinned runtime release. Provider access comes from the user's OpenCode configuration, and the adapter must not read credentials beyond what the engine itself holds.

### Authentication for agent engines

dev-org must use each engine's supported authentication without requiring separate credentials by default: OpenCode through its configured provider APIs, and Codex/ChatGPT and Claude Code through their vendor subscription logins. Authentication happens through the engine's own configuration and runtime; dev-org must not fetch, decode, or forward raw login tokens, subscription tokens, or provider keys between users or engines.

- **OpenCode:** run the pinned, unmodified OpenCode CLI with the user's own provider configuration (for example chutes, openrouter, or anthropic). The user's credentials stay in the OpenCode configuration and the OS credential store; dev-org does not offer a login, does not collect provider keys, and does not route usage through a shared account. The adapter must demonstrate that agent tools cannot read the provider credentials beyond what the engine itself holds; if that cannot be enforced, the provider profile cannot be used in that operating mode.
- **Codex:** use Codex App Server with the user's supported ChatGPT plan login. If dev-org must implement its own login with Sign in with ChatGPT, the official plan-usage flow for qualified open-source/locally run clients applies and requires the user's explicit consent. Hosted or commercial distribution must not assume this capability is approved; clarify provider approval first. The App Server version is pinned, thread ID is stored only as a runtime reference, and authorization is held in the provider's or OS's secure credential store. See [Codex App Server with ChatGPT plan usage](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server) and [an overview of Sign in with ChatGPT](https://developers.openai.com/siwc/token-sharing-open-source).
- **Claude Code:** run the unmodified, Anthropic-published Claude Code binary. The user logs in themselves with their Claude account through Claude Code's own flow; dev-org does not offer a Claude.ai login, does not collect subscription tokens, and does not route Claude usage through a shared account. If dev-org is distributed or run as a product/service for others, Anthropic's Commercial Terms and the terms for each end user authenticating with their own account must be followed; on doubt, usage must be clarified with Anthropic before the adapter is activated. See [Anthropic's Claude Code legal and authentication terms](https://code.claude.com/docs/en/legal-and-compliance).
- **Credential isolation:** authentication state is tied to a named subscription owner or provider profile and an approved worker. It must not be mounted in the task container, the agent's shell/tool environment, or the repo. Adapter qualification must demonstrate that agent tools cannot read or use the credential; if that cannot be enforced, the credential cannot be used in that operating mode.
- **Quota and billing:** the provider's subscription quotas, provider-API limits, and concurrency limits are respected per account. On quota/rate limit the work is paused and resumes after the provider's reset or after an explicit choice of another authorized account or provider profile. Automatic transition to a different payment model is forbidden. A new provider profile, API key, or payment arrangement can only be used as a separate, explicitly configured choice with its own cost limit and clear marking.

The official terms are part of the adapter qualification. If a provider's authentication model or terms change, the adapter must be set to a "needs clarification" status before further use with that account or profile; other qualified engines and tasks must be able to continue.

The first delivery scope is one pilot organization, one GitHub repo and issue, one active agent run at a time, opening one PR, waiting on mandatory GitHub Actions checks, and updating the issue/status. The pilot repo can be the dev-org repo. The local board adapter is used for development and contract tests; moving the pilot's active backlog can be done with explicit export/import, but automatic two-way synchronization is not included. No agent-driven merging, rollout, physical bench, general agent-to-agent organization, or background optimization is included. These remain represented in the architecture but cannot be triggered in the MVP.

The default profile per attempt container is at most 2 CPU cores, 4 GiB memory, 256 processes/threads, 20 GiB writable workspace, and 90 minutes wall clock time. Total active model running additionally has the limit in section 10.4. The worker interrupts the attempt on exceedance and secures the workspace first when it is safe. The owner can set lower limits per project; higher limits require a versioned profile change and a controlled measurement of the worker's capacity.

### 10.3 Identity, rights, and approval

Operators log in via GitHub OAuth with only `read:user` and `user:email`; only explicitly allowed GitHub users for the pilot organization get access. Roles are `owner`, `approver`, `operator`, and `observer`. Worker nodes are authenticated with project-scoped, revocable tokens stored hashed. GitHub App installation tokens are obtained short-lived by the gateway; they must never be sent to the agent process or mounted in the sandbox. OpenCode runs as the engine process outside the attempt container. Any model access is scoped to this process; the agent's shell, tool processes, and container get no model or GitHub credentials in environment variables, files, or mounts.

In the MVP `owner` gets `access.inspect_others` within the pilot organization and its chosen projects. `approver`, `operator`, `observer`, and worker/agent identities can inspect their own effective access; they can inspect others only with an explicit, scoped addition. Insight never grants the right to change mandates. The role view shows the role estimate, while viewing an agent shows its effective access in the chosen project and task context.

The GitHub App is installed only on the pilot repo and chosen organization. It gets metadata read, contents read/write for branch publishing, issues read/write, pull requests read/write, checks read, commit statuses read, Actions read, and organization Projects read/write for the chosen project. It does not get Workflows, Administration, Secrets, or Deployments rights. Agent changes in `.github/workflows/` are therefore blocked in the MVP. The setup validates the necessary minimum rights; a request for extended rights stops startup until the owner has changed and versioned the policy. Endpoints with other concrete requirements must be covered by the fewest possible additional permissions before implementation.

The default mandate profile for the MVP:

| Action | Default |
|---|---|
| Read issue, repo, history, and CI status | Allowed within the chosen project and repo. |
| Change files, run tests, and build | Allowed only in the attempt container and within the resource profile. |
| Create/push a working branch, open a PR, and update the issue with status/PR link | Allowed via the gateway when the issue is reserved and policy requirements are met. |
| Approve your own PR, merge, change branch protection, workflow, or GitHub App rights, publish a release, or roll out | Direct agent action is denied in the MVP. After the MVP a separate promotion service can merge and activate low-risk changes within a standing, owner-approved mandate. Changes to workflow files, protected control areas, and rights require special owner decision. |
| Change mandates, project mapping, approval rules, or isolation profile | In the MVP: only `owner` via the control UI and with a versioned audit event. Later: the policy service can change these autonomously within a versioned, pre-delegated base frame and after qualified gates. Extending the base frame still requires an owner decision. |

No agent may approve its own action or issue an approval on behalf of the policy. For low-risk work the owner's standing mandate can give the promotion service the right to merge after passing checks without a human decision per PR. When a concrete human approval is required, it is bound to commit SHA, PR, passing checks, and the current policy version; the PR's owner cannot approve it alone. Such approvals expire after 24 hours and become invalid on a change of commit or scope.

### 10.4 Operational targets for the pilot

The pilot is a single node without an HA guarantee. The following are acceptance targets, not uptime guarantees:

| Target | Pilot target |
|---|---|
| Webhook to durable registration | 99% within 10 seconds when the service is available. |
| Ready issue to worker start | p95 within 30 seconds with a free qualified worker. |
| Approved external event to resume | p95 within 60 seconds. The polling fallback gives discovery within 2 minutes. |
| Alert on control service/DB failure | Within 5 minutes after the health check fails. |
| Recovery | RPO at most 15 minutes and RTO at most 1 hour after a recovery test. |
| Event retention | 90 days for structured events; detailed debugging log 14 days. Full conversation transcripts are not stored by default. Artifacts follow the project's storage rule. |
| Agent budget | At most 3 attempts and 60 minutes of active model running per issue as the starting profile. One active attempt per repo. A provider cost cap is configured when it can be enforced; otherwise cost is recorded as unknown and the time/attempt caps are enforced. |

The pilot must block new publishing actions if the database or required audit registration is unavailable. On a short control service failure the runner can preserve local work, but must not push or change external state before it has renewed the reservation and checked the current policy.

### 10.5 Security boundary and later choices

Rootless Podman reduces access and isolates processes, but shares the host kernel and must not be presented as strong isolation against an active kernel or container runtime attack. The pilot's threat model is unintentional or prompt-driven agent actions in one controlled repo. Projects running deliberately hostile code, several mutually untrusted customers, or needing stronger isolation must use a VM-based backend before they are onboarded. A new backend is implemented behind the execution environment contract and must pass A20–A21.

The following cannot be extended in the MVP without an ADR: database product, API format, event envelope, authoritative IDs, first GitHub App installation model, default mandate profile, first agent engine, and the sandbox's default network policy. The hosting platform, UI framework, and future message broker can change as long as contracts and acceptance requirements pass.
